# UNIVERSAL MCU / MEMORY PROGRAMMER

## Professional Tkinter GUI + Arduino Firmware ESP32 Board

Build a professional Windows-based Universal Programmer consisting of:

1. A modern Python Tkinter GUI application.
2. Arduino firmware that acts as the hardware programming interface.
3. A modular protocol architecture so additional IC families can be added later without redesigning the entire application.

The initial target platforms are:

- AVR ISP with Support ATtiny85 also
- SPI memory devices
- I²C memory devices

The architecture must be extensible for future protocols such as 1-Wire and other custom serial protocols.

---

## 1. IMPORTANT EXISTING FIRMWARE

Use the supplied ArduinoISP sketch as the starting/reference firmware.

Do not unnecessarily remove or break its existing AVR ISP functionality.

The supplied firmware already implements concepts including:

- Arduino-to-target SPI communication
- Target RESET control
- AVR programming mode
- Device signature reading
- Flash reading
- EEPROM reading
- Flash programming
- EEPROM programming
- STK500/AVRISP-style serial commands

Preserve these capabilities while restructuring or extending the firmware where necessary.

- Detect available COM ports.
- Refresh COM ports.
- Connect/disconnect from Arduino.

- Handle Arduino disconnect/reconnect gracefully.

# 6. AVR ISP SUPPORT

Implement proper AVR ISP functionality based on the supplied ArduinoISP firmware.

- Determine memory size when supported
- Read Flash
- Read EEPROM

# 9. READ DUMP FUNCTION

This is a critical requirement.

When the user clicks:

```
READ FLASH
```

the software must:

1. Detect/validate the target.
2. Enter programming mode.
3. Read the complete selected memory.
4. Store the bytes in an in-memory buffer.
5. Update the hex viewer progressively or safely after chunks.
6. Update progress percentage.
7. Calculate checksum/hash after completion.
8. Allow the user to save the dump.

For:

```
READ ALL
```

read all supported memory areas and keep them separately.

Example:

```
flash.bin
eeprom.bin
```

Do not overwrite an existing dump without asking the user.

# 12. WRITE / PROGRAM

When the user selects:

```
WRITE
```

the application must:

1. Require a loaded binary or selected memory buffer.
2. Detect/validate target.
3. Validate size.
4. Ask for confirmation before programming.
5. Program the device.
6. Display progress.
7. Report errors precisely.
8. Optionally perform automatic verification.

Recommended workflow:

```
Detect
  ↓
Load BIN
  ↓
Validate size
  ↓
Write
  ↓
Verify
  ↓
SUCCESS
```

# 30. CRITICAL REQUIREMENT

The most important requirement is:

**READ FROM TARGET DEVICE → STORE THE ACTUAL BYTES → DISPLAY THE DUMP → SAVE THE ACTUAL DUMP AS&#x20;****`.BIN`****.**

The application must not merely show a simulated dump or generate placeholder data.

The bytes saved to the `.bin` file must be the actual bytes received from the target device.

Likewise, when programming a device, the bytes sent must come from the selected binary buffer/file.
